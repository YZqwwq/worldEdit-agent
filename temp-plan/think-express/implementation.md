# 实施顺序与验收

更新时间：2026-09-12。状态：待实施；本文件区分代码事实、历史测试现象与拟议方案。

## 原则

复用现有 Agent 图、工具发布与 Turn 提交、contentJson 和隔离测试。按用户可观察行为交付，不先抽取内核或新增独立表达 Agent。固定风格模板不能替代协议改造。

## P0：建立新的验收基线

在既有 testarea/scenarios 中按用途增加场景，运行 probe:agent-scenario，使用隔离数据库。普通交流用 user，测试身份语义用 tester；需要文档的用固定 fixture，空白交流用 empty/fresh。

保留原 multidimensional-character/design 场景，但不将“场景跑完”视为表达质量通过。读取、印象查询、精确输出的失败仍保留，不反复放宽断言。

验收分为确定性断言和人工语义审计：

| 场景 | 自动检查 | 人工检查 |
| --- | --- | --- |
| 简单事实 | 实际读取、事实关键内容、无非必要写入 | 简洁准确，没有强造延伸 |
| 有讨论空间的材料 | 当轮交接存在、工具结果对应目标 | 候选有区别、依据明确、表达只选部分 |
| 完整长方案 | artifact 正文存在且 committed、引用可解析 | 内容完整，聊天仅保留重点，不重复全文 |
| 用户要求直接全文 | 本轮交付形式符合要求 | 不强制转卡牌，不丢内容 |
| 卡牌工具失败 | 无假引用、无重复写入、失败状态可见 | 不声称已交付，说明真实完成情况 |
| 精确结果 | responseEquals | 不追加候选、卡牌或额外标点 |
| 多段输出 | 数量/顺序/ID 持久化一致 | 每段独立完整，不把长文碎片化 |
| 刷新与撤回 | 历史恢复一致、无重复、撤回范围正确 | 气泡与卡牌归属直观 |
| 用户中途新消息 | 旧投递队列停止、重试不重复 | 不把未展示部分当作用户已收到 |

需要扩展既有 runner 的 artifact/分段断言，不能仅检查调用名称或回复包含“卡片”。UI 以浏览器/应用截图及交互测试验证，不能只看序列化单测。

## P1：短正文与独立长内容

1. 在 expression 明确正文与独立产物的分配职责，沿用 publish_agent_artifact；不新增平行的文件存储工具。
2. 检查长内容素材如何穿过 cognition handoff，避免 4800 字符限制把交付正文截掉；先以真实长方案定位问题，再选择载体，不机械扩大所有上下文。
3. 验证发布工具在 expression 的可用性和失败恢复。工具生成 draft 后仍需 Turn 提交，只有真实 committed 产物才能对外形成成功交付。
4. 验证正文不重复卡牌全文；卡牌数量、重复发布与失败后重试由运行时检查，不只靠 prompt。
5. 保留主线优先和候选依据；简短不是删掉关键事实，长内容转卡牌不是减少任务完成度。

完成标准：短问答不滥发卡牌，长内容可打开且完整，聊天承担重点；失败、中断、重试没有假成功或重复产物。

## P2：同轮多气泡贯通

1. 定稿消息单元契约：有序文本单元及稳定 ID，与 Turn/message 关联；保留单个逻辑 Turn。
2. 改造模型输出解析、FinalContentCandidate 和 Output Guard。类型错误、空段、超出资源上限时明确处理，不能把 JSON 回退成用户正文。
3. 在 committer/contentJson 中保留单元边界与卡牌引用；content 是检索投影，不作为 UI 分段的重新推断来源。
4. 同步 IPC/stream 载荷和 aiClientService；不能再将多个文本单元 join 成单个气泡。
5. 检查聊天组件、历史加载、复制、编辑、撤回和卡牌打开的行为。保留 Turn 的原子提交与恢复，不先引入多个独立提交事务。

完成标准：同一次回应的独立内容显示为有序气泡；刷新后结构一致；卡牌不在每个气泡重复；完整性不依赖人工分隔符。

## P3：逐条呈现与中断

第一版多气泡可以一次提交后呈现，不需要假装逐条生成。若后续加入打字间隔和逐条展示，先设计投递状态再做动画：

- 区分已生成、已提交、已展示及尚未展示。
- 新用户消息到达时取消剩余旧展示队列，避免旧话题插入新回复。
- 重连和重试按单元 ID 幂等恢复。
- 明确历史和生活状态如何处理未展示内容；不可将已生成等同已对话。
- 跨轮继续展开由用户反馈决定，不通过定时器主动发完所有候选。

## 风险与未决项

- 多维思考目前存在过度推断；发布为卡牌不会让结论更可靠。
- 当前 handoff 主要接通 emulated 路径，native 需要独立验证。
- 历史中已保存的单文本消息需按其真实结构展示；不要推测旧气泡分段，也不进行无必要的数据重写。
- UI 独立气泡是否需要独立消息级撤回，还是整个 Turn 撤回，需要与现有撤回规则统一；默认先保留 Turn 级所有权。
- artifact 是数据库中的 Markdown 内容，不是操作系统文件。若用户需要下载/磁盘文件，需要另行设计导出，不应冒充已有能力。
- 不设“每轮必须多想几个方向、发几条消息”的硬指标。数量与长度仅用于诊断倾倒问题。

## 建议首个实施单元

先完成 P0 中短答、长内容卡牌、失败三类场景，再推进 P1。卡牌链路已有基础，最容易先给用户可见收益。P2 需要协议、提交和前端共同修改，应作为独立完整变更验收。
